# Claude Code Guidelines

## About this repo

Personal macOS dotfiles for managing a consistent development environment across machines. Uses [GNU Stow](https://www.gnu.org/software/stow/) for symlinking configs, a `Makefile` for bootstrapping a fresh machine, and a `dot` CLI (TypeScript, compiled with Bun) for day-to-day maintenance. Designed to be idempotent — `make` is safe to run multiple times.

## Documentation

Whenever new functionality is added, update all relevant documentation points:
- `CLAUDE.md` — add any new key files, stow layout changes, or behavioral guidelines
- `README.md` — update user-facing docs (new commands, targets, tools, install steps)
- `src/dot.ts` — if a new `dot` subcommand is added, define it there with Commander (`.command().description().action()`); its help comes from those descriptions
- `install/Linkfile` — if a new individual (non-stowed) symlink is introduced
- `health` in `src/commands/health.ts` — if new tools or runtimes are introduced (individual symlinks come from `install/Linkfile`)
- `completions/` — if a new `dot` subcommand is added, update the shell completions

## dot health

Every check in `src/commands/health.ts` names the `Fix` that resolves it (usually `makeFix("<target>")`). Failed runs list each fix's command once, and `dot health --fix` runs them all and then re-checks. A new check needs a fix too, and its target must be idempotent, since `--fix` may run it on a machine that is mostly set up already.

Individual symlinks need no `dot health` change — add a `source|destination` line to `install/Linkfile` and `make link`, `make unlink`, `dot health`, and `make test-link` all pick it up. Never hardcode an individual symlink path in more than one place; that drift is what `install/Linkfile` exists to prevent.

Cask apps need no `dot health` change either — add a `cask "name"` line to `install/Caskfile` and `make cask-apps`, `dot install`, and `dot health` all pick it up through `dot casks`.

Login items need no `dot health` change either — add an absolute `.app` path line to `install/Loginfile` and `make login-items` and `dot health` both pick it up.

macOS defaults need no `dot health` change either — add a `domain|key|type|value|restart` line to `install/Defaultsfile` and `make macos-defaults`, `dot install`, and `dot health` all pick it up through `dot defaults`.

Always update the `health` function in `src/commands/health.ts` when:
- A new required tool is added to the setup (brew, stow, asdf, etc.)
- A new asdf runtime is added to `runcom/.tool-versions`
- The commit-signing setup changes (`config/git/allowed_signers`, `make signers`)
- A new Mac App Store app is added to `install/Masfile`
- A new Claude Code plugin is added to `install/Pluginfile`
- A new Claude Code skill source is added to `install/Skillfile`

## Key files

- `src/dot.ts` — entry point of the `dot` CLI (TypeScript). Commands are a [Commander](https://github.com/tj/commander.js) tree: dispatch, `--help`, `dot help <command>`, option parsing, unknown-command errors, and help wrapping all come from it, so never hand-roll any of those. Help is styled through `configureHelp`/`configureOutput` with `colors.ts`, whose detection (including `CLICOLOR_FORCE`) wins over Commander's. A bare `dot` or `dot casks`/`dot defaults` prints help to stdout and exits 0; Commander would otherwise treat it as an error. Commands that report pass/fail set `process.exitCode` instead of calling `process.exit()`. Commands live in `src/commands/` (`setup.ts` for install/update/clean/edit, `health.ts`, `casks.ts`, `defaults.ts`), shared code in `src/lib/` (`manifest.ts` parses every `install/*file`, `proc.ts` runs commands, `paths.ts` locates the repo, `colors.ts`, `spinner.ts`). Imports use the `@/` alias for `src/` (`tsconfig.json` `paths`, which Bun and `tsc` both resolve), never relative `./` or `../` paths — Biome's `noRestrictedImports` rejects them. Tests sit next to the code as `*.test.ts` (`bun test`); `bun run typecheck` runs `tsc`; `bun run check` runs lint, typecheck, and tests together. Child processes are spawned asynchronously (`Bun.spawn`, never `spawnSync`) so the SIGINT handler in `casks repair` and the sudo keepalive in `update` can actually run. Output goes through `writeSync` so it never interleaves out of order with child output. Wrap silent work (anything awaiting `capture`/`succeeds`) in `spin()` from `src/lib/spinner.ts` so the screen never sits frozen; never wrap `run()`, whose streamed output and sudo prompts share the terminal. The spinner draws on stderr only when stderr is a TTY, so captured stdout (`make demo`) stays free of frames. In `dot update`, per-item steps that need no terminal (VS Code extensions, npm globals, Claude plugins) go through `updateEach` in `setup.ts`: a spinner per item, then one ✓/✗ line, instead of each tool's streamed chatter
- `biome.jsonc` — Biome lint and format config for `src/`. JSONC because Biome cannot load a JS/TS config; the comments next to each non-default rule hold its rationale, so keep them current when a rule changes. Beyond the recommended preset it enforces the `@/` import alias (`style/noRestrictedImports`) and un-awaited promises (`nursery/noFloatingPromises`, type-aware). `bun run lint` checks, `bun run fix` applies formatting, import sorting, and safe fixes.
- `.githooks/pre-commit` — runs `bun run check` before any commit touching `src/`, `package.json`, `tsconfig.json`, `biome.jsonc`, or `bun.lock` (installing dev dependencies first if `node_modules` is missing). Enabled per clone by `make git-hooks`, which sets `core.hooksPath`; `dot-bin` depends on it, so any build of `dot` (including the shim's automatic rebuild) turns it on with no manual step. `dot health` checks it under Commits. Never wire lint into `make dot-bin`: a lint error must not stop `dot` from building during `make` or `dot update`
- `bin/dot` — committed shell shim and the only `dot` on `PATH`. It rebuilds `.build/dot` via `make dot-bin` when that binary is missing or older than `src/`, `package.json`, `tsconfig.json`, or `bun.lock` (about 10ms of overhead per call), then `exec`s it. This is what makes a pull, a fresh clone, or a new machine need no manual build step — never require the user to run a build by hand. Keep the shim tiny; logic belongs in `src/`
- `.build/dot` — gitignored build output, never edited or committed. `make dot-bin` runs `bun install --frozen-lockfile` (Commander is bundled in, so a fresh clone needs `node_modules`) then compiles it with `bun build --compile` (~85MB standalone binary, no runtime needed to run it), and only rebuilds when `src/`, `package.json`, `tsconfig.json`, or `bun.lock` changed. It builds to a temp file and renames it, because overwriting the binary in place while `dot update` is running it gets that process killed by macOS code signing; it also deletes the `.*.bun-build` temp file Bun leaves in the working directory. `dot-bin` is the first `MACOS_STEPS` entry and a prerequisite of every target that calls `dot` (`cask-apps`, `macos-defaults`, `demo`); `dot update` re-runs it after `git pull`, and the `bin/dot` shim runs it on demand. Bun comes from `install/Brewfile`, and the recipe installs it itself if absent. The repo root is found from the executable path, since compiled modules live in Bun's virtual `/$bunfs`; `DOTFILES_DIR` overrides it
- `lib/colors.sh` — shared output helpers (`pass`, `fail`, `warn`, `info`, `note`, `section`, `step`, `success`, `error`) sourced by the Makefile (recipes that print start with `$(COLORS)`). `src/lib/colors.ts` mirrors them for `dot`; change both together. Uses only the 16 ANSI colors so the terminal theme (Catppuccin via Ghostty) supplies the actual shades and follows light/dark — never hardcode hex/truecolor escapes. Color is off when stdout is not a TTY or `NO_COLOR` is set. New scripts and new output lines should go through these helpers (or their `colors.ts` twins) rather than raw `printf "  ✓ ..."`, so status colors stay consistent everywhere
- `docs/dot-health.tape` — [VHS](https://github.com/charmbracelet/vhs) script for the README GIF (`docs/dot-health.gif`). Always regenerate with `make demo`, never `vhs` directly: the target records a real `dot health` run with `script -r` (timestamped, in a real pty, so the spinner and colors are captured) into the gitignored `docs/.dot-health.rec`, and the tape plays it back in real time with `script -q -p` (`-q` drops the "Script started/done" banners). Running the checks live inside VHS hangs on the login-items `osascript` call, which needs Automation permission VHS's headless terminal does not have. The GIF shows the recording machine's real state. The GIF is as long as the recorded run; the tape `Wait`s for the final `checks passed|failed` line instead of a fixed `Sleep`, so keep that summary wording in sync with `health.ts`. If the report grows, raise `Set Height` so the whole report still fits on one screen
- `dot casks` (`src/commands/casks.ts`) — verifies that every cask in `install/Caskfile` has its App and Binary artifacts on disk, not just a Homebrew receipt. `dot casks check` reports and exits non-zero on drift; `repair` reinstalls the broken ones (falling back to a forced uninstall/install) and re-checks. Binary artifacts are matched against their declared target path, which is frequently absolute and outside the Homebrew prefix (`docker-desktop` links into `/usr/local/bin`) — checking only `$(brew --prefix)/bin` made such casks read as broken forever and `make cask-apps` never converge. `repair` primes sudo once on the real terminal before touching any cask and bails out with a hint instead of hanging when there is no terminal to prompt on, clears dangling `/Applications` symlinks itself so Homebrew's sandbox never has to ask for root, and re-derives the broken set on every run so an interrupted repair is fixed by re-running it. It also flags an App bundle not owned by the current user (self-updating apps like Slack can leave theirs root-owned, which makes `brew upgrade` fail with `Permission denied @ apply2files` and strand a backup in the Caskroom); `repair` fixes that with `sudo chown -R` instead of a reinstall. macOS App Management blocks that `chown` even as root unless the terminal is granted App Management in Privacy & Security, so a failure there is a permissions prompt to resolve, not a script bug. Both `make cask-apps` and `dot install` run `dot casks repair` after `brew bundle`, and `dot update` runs it before `brew upgrade`; `dot health` runs `check`. Plain `brew upgrade` skips `auto_updates` casks, which then never move when the app's own updater is off or on another channel, so `dot update` follows it with `upgradeSelfUpdating`. Never go back to a blanket `brew upgrade --greedy-auto-updates`: Homebrew judges those casks from its receipt, not the app on disk, so once an app's updater has moved past the cask definition the greedy upgrade installs the older release over it (it downgraded OneDrive, which then refused to open its sync database). `upgradeSelfUpdating` reads each outdated cask's installed `CFBundleShortVersionString` (from its App artifact, or for pkg casks the `.app` in its uninstall `delete` list) and upgrades only casks whose app is older than the cask or missing; an app it cannot read is left to its own updater. `extras` lists installed casks absent from the Caskfile (a warning in `dot health`, never a failure) and `prune` uninstalls them, confirming each cask individually (`--all` asks once for the whole list). Never wire `prune` into `make` or `dot install` — uninstalling deletes apps, so it stays an explicit, confirmed action. Adding a cask to `install/Caskfile` is all that's needed — never hardcode a cask name anywhere else
- `Makefile` — full machine setup, idempotent and safe to re-run. `macos` iterates `MACOS_STEPS` through recursive make rather than listing them as prerequisites, so one failing step still lets the rest run; failures are collected and reported, and the target exits non-zero. Keep new setup steps in `MACOS_STEPS`, not in the prerequisite list, or a failure there will strand everything after it. The `sudo` target primes the credential cache and keeps it warm for the lifetime of the make process (it watches `$$PPID`), because `cask-apps` can need root minutes in and macOS expires the timestamp after 5 minutes. It degrades to a warning when there is no tty instead of failing, so unattended runs still work. Every loop that reads an `install/*file` uses `read -r ... || [ -n "$$var" ]` so a file with no trailing newline does not silently lose its last entry
- `runcom/.zshrc` — zsh config, symlinked to `~/.zshrc` via stow
- `runcom/.tool-versions` — asdf runtime versions, symlinked to `~/.tool-versions` via stow
- `system/` — shell config files sourced by `.zshrc` on every terminal open
- `system/.dotfiles-update` — auto-update check, runs every 7 days
- `install/Brewfile` — Homebrew packages
- `install/Caskfile` — Homebrew cask apps, including font casks. Any font named in `config/ghostty/config` belongs here: Ghostty renders the terminal grid in a font it resolves itself even when nothing is installed system-wide, so a missing font cask is invisible until some other consumer (AppKit, another app) needs the family name and silently falls back
- `install/Masfile` — Mac App Store apps (`name|id` per line, installed via `mas`, requires the `mas` brew and being signed into the App Store)
- `install/Codefile` — VS Code extensions
- `install/Npmfile` — global npm packages. Symlinked to `~/.default-npm-packages` via `install/Linkfile`, so the asdf nodejs plugin installs them into every newly installed Node version. asdf keeps globals per Node version, so without this a version bump in `runcom/.tool-versions` leaves the shims with "No version is set for command"
- `install/Mcpfile` — Claude Code MCP servers (`name|command` per line, registered at user scope via `claude mcp add`)
- `install/Pluginfile` — Claude Code plugins (`plugin@marketplace|source` per line). `make claude-plugins` adds the marketplace then installs the plugin at user scope, skipping either step if already present. Note that plugins can register hooks that run on every session start and prompt submit, so review a plugin's `.claude-plugin/plugin.json` before adding it here.
- `install/Skillfile` — Claude Code skill sources installed via the [`skills` CLI](https://www.npmjs.com/package/skills) (one GitHub `owner/repo` source per line). `make claude-skills` runs `npx skills add -g -y <source>` for each, skipping sources already present in the global skill list. The tool owns the actual state — skills land in `~/.agents/skills/*` (source of truth, outside this repo) and are symlinked into `~/.claude/skills/*`; it also maintains its own lockfile at `~/.agents/.skill-lock.json`. To update installed skills to their latest versions, run `npx skills update -g`. A single source can install multiple named skills — review what a source actually installs (`npx skills add -g -s '*' -l <source>` lists without installing) before adding it here.
- `dot defaults` (`src/commands/defaults.ts`) — applies (`apply`) and verifies (`check`) macOS preferences from `install/Defaultsfile`. Booleans are normalized before comparing (`defaults read` prints 1/0), so runs converge; the restart app is only killed when a value actually changed
- `install/Defaultsfile` — macOS `defaults` settings (`domain|key|type|value|restart` per line, restart `-` for none). Applied by `make macos-defaults` and `dot install`, drift-checked by `dot health`. Adding a line is all that's needed — never hardcode a defaults key anywhere else
- `install/Loginfile` — macOS login items (one absolute `.app` path per line). `make login-items` registers each via osascript + System Events, skipping apps not on disk and entries already present (matched by path substring, since apps like OneDrive register a helper inside their own bundle); `dot health` checks each entry. Login items live in the Background Task Management database, so `defaults` can't manage them; first run prompts once for Automation permission over System Events. Adding a line to the file is all that's needed
- `install/Linkfile` — individual symlinks (`source|destination` per line, `$HOME` in the destination is expanded at link time). Single source of truth for every symlink that isn't stow-managed: `make link-files` creates them, `make unlink` removes them, `dot health` verifies them, `make test-link` round-trips the pair. Use it for app-managed directories where stow would conflict with state the app writes itself.
- `claude/` — Claude Code settings, statusline, and skills (symlinked individually via `install/Linkfile`, not stowed)
- `config/ghostty/config` — Ghostty terminal config, stowed to `~/.config/ghostty/config`. `font-family` is resolved by Ghostty itself, but `window-title-font-family` is resolved by AppKit (`NSFont`), which only sees system-installed fonts and falls back to the system font without any error when the name does not resolve — verify a family with `osascript -l JavaScript -e 'ObjC.import("AppKit"); $.NSFont.fontWithNameSize("Family", 13).isNil()'` before assuming the setting is ignored. Window chrome settings only apply to windows opened after a config reload
- `config/git/allowed_signers` — shared SSH signature-verification allowlist, one `identities key` line per machine. The *signing* key is per-machine and lives in the gitignored `~/.config/git/local`; this file is the union of every machine's public key and is committed. `make signers` appends the current machine's key idempotently.

## Stow layout

- `runcom/` is stowed to `$HOME`
- `config/` is stowed to `$HOME/.config` (e.g. `git`, `ghostty`)
- `system/` is sourced directly from `~/dotfiles/system/`, not stowed
